# 取码接口的 HTML 形态原样返回邮件正文，不做净化

`GET /api/v1/otp?format=html` 的用途是让人真正看到并点击邮件里的图片和按钮，而邮件 HTML 是发信人可控的第三方内容。按常规做法做标签白名单净化会废掉这个形态存在的理由——邮件 HTML 大量依赖内联样式与嵌套表格，任何白名单都会漏掉某些发信人的标记，结果是"净化完按钮点不动"。

因此决定原样返回正文字节，把防护放在响应头而不是内容上：该响应保留全局 CSP 的 `script-src 'self'`（邮件内脚本不执行）、`base-uri 'self'`（阻止邮件塞 `<base>` 劫持正文里的相对链接）与 `frame-ancestors 'none'`，只放宽 `img-src` 以允许外链图片，并把 `form-action` 收紧为 `'none'`。

代价是明确接受的、而非意外：发信人可以用 CSS 做界面伪装（在页面上画一个假登录框），也可以通过外链图片 URL 得知取码页何时被打开。接受它的理由是访问该 URL 的正是凭据持有人本人；但也正因 URL 里的 OTP token 本身就是凭据，`script-src` 绝不放开。

放行的只有发信人**确实提供**的 HTML。邮件只有纯文本时，该文本会被转义后以等宽块显示——那一段是服务自己生成的标记，经过转义，所以纯文本里看起来像标签的内容会原样可见而不会变成活标记。没有 HTML 部件的纯文本邮件因此不会退化成空白页。

## Considered Options

- **标签白名单净化**：如上，会破坏该形态的核心用途。
- **服务端图片代理**：能同时解决外链图片的回传问题，但为一个内部工具引入图片代理不值得。
- **`sandbox` iframe 包裹**：会让链接跳转行为与页面渲染都变形，收益不抵复杂度。

## Status

已接受，2026-10-13。其中「`sandbox` iframe 包裹」的取舍已被 ADR 0002 取代；「不净化邮件 HTML」的核心决定继续有效。
